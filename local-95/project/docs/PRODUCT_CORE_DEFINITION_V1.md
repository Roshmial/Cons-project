## 1. Зачем нужен продукт

Hermes должен стать единым внутренним инструментом автоматизации текущих задач и процессов компании.

Его задача — не конкурировать с уже внедрённым корпоративным LLM-чатом на поле «универсального диалогового помощника», а закрывать тот класс задач, где нужен не только ответ, но и рабочий результат:
- регулярное выполнение по расписанию;
- мониторинг источников и состояний;
- работа с пользовательскими материалами и файлами;
- генерация структурированных результатов;
- передача результата во внутренний рабочий или интеграционный контур.

Главная идея продукта:
Hermes — это не просто AI-chat, а AI-слой исполнения, повторяемости и операционной полезности.

## 2. Отстройка от корпоративного LLM-чата

Корпоративный LLM-чат закрывает базовый слой:
- вопрос-ответ;
- быстрые текстовые консультации;
- общие conversational сценарии.

Hermes должен отстраиваться по другому обещанию ценности:
- recurring jobs и cron-сценарии;
- monitoring и digest workflows;
- запуск и повторяемость задач;
- files и artifacts как first-class сущности;
- handoff в рабочий контур;
- admin / policy / operational layer.

Ключевая формулировка позиционирования:

Hermes — это внутренний AI-инструмент для регулярной работы, мониторинга, файлов, артефактов и операционного handoff.

## 3. Продуктовая цель

Сделать Hermes рабочим внутренним продуктом, который:
- устойчиво закрывает повседневные прикладные задачи;
- позволяет собирать и исполнять recurring workflows;
- не ломается на не прибитых к полу сценариях, а деградирует управляемо;
- даёт результат, который можно использовать дальше без ручной расшифровки;
- может быть встроен во внутренний контур компании как слой автоматизации и orchestration.

## 4. Приоритеты продукта

### Приоритет 1. Recurring scenarios / cron / monitoring

Это главный differentiator продукта.

В этот слой входят:
- recurring jobs;
- cron-based automation;
- регулярные мониторинги;
- digest-сценарии;
- triage / review / audit jobs;
- backup / sync / periodic operational tasks;
- подписки и доставка результатов.

Почему это приоритет №1:
- именно здесь Hermes сильнее обычного LLM-чата;
- именно здесь появляется повторяемая бизнес-полезность;
- именно здесь возникает эффект единого инструмента автоматизации.

### Приоритет 2. Чат-помощник

Чат-помощник нужен, но не как самоцель.

Его роль:
- собирать информацию;
- делать прикладной research;
- считать модели и расчёты;
- генерировать таблицы;
- собирать структурированные выводы;
- переводить запрос из разговора в job / artifact / handoff.

Чат в продукте — это точка входа и рабочая оболочка, а не единственный смысл системы.

### Приоритет 3. Обработка и генерация файлов

Файлы должны стать отдельным продуктовым контуром, а не побочной функцией attachment'ов.

В этот слой входят:
- intake пользовательских файлов;
- extraction и parsing;
- reuse файлов в новых задачах;
- генерация файлов как deliverable;
- понятный lifecycle файлов;
- связь file -> artifact -> handoff.

### Приоритет 4. Дашборды

Дашборды — допустимый и полезный слой, но не центр продукта на текущем этапе.

Их роль:
- визуализировать уже полезный результат;
- усиливать monitoring и analytical output;
- служить вторичным способом представления данных.

Что важно:
- dashboards не должны вытягивать на себя основную продуктовую энергию раньше, чем стабилизированы recurring workflows, assistant core и file contour.

## 4A. Будущий workflow layer

Отдельным стратегическим слоем в будущем должен стать workflow layer.

Его смысл:
- связывать chat, jobs, files, artifacts и handoff в более цельные рабочие цепочки;
- оформлять повторяемые бизнес-процессы в понятные сценарии исполнения;
- давать переход от разового запроса к устойчивому workflow.

Важно:
- workflow layer не должен сейчас размывать core и конкурировать с приоритетом recurring / assistant / files;
- его надо строить поверх уже устойчивого продуктового ядра, а не вместо него.

На текущем этапе workflow layer — не первый delivery-приоритет, а следующий системный слой после стабилизации core-сценариев.

## 5. Целевые пользовательские группы

### 5.1 Обычный сотрудник
Нужны:
- быстрые прикладные ответы;
- помощь с материалами;
- возможность запустить или получить полезную регулярку;
- понятный итоговый результат.

### 5.2 Power user / владелец процесса
Нужны:
- recurring jobs;
- monitoring-сценарии;
- ручной запуск задач;
- подписки на результат;
- артефакты, пригодные для дальнейшей работы.

### 5.3 Admin / operator
Нужны:
- контроль здоровья системы;
- users / jobs / events / policy;
- управление operational rules;
- контроль деградаций, ошибок и стабильности.

### 5.4 Интеграционный контур
Нужны:
- handoff результата из Hermes;
- structured outputs;
- понятные артефакты;
- предсказуемая передача в дальнейшие внутренние процессы.

## 6. Core entities

Это сущности, которые должны быть явно оформлены и разведены в продукте.

### Chat
Используется для:
- постановки задачи;
- уточнений;
- диалога;
- получения ответа;
- перехода к job / file / artifact / handoff.

### File
Используется для:
- входных материалов;
- повторного использования;
- извлечения текста;
- обработки и генерации.

### Artifact
Используется для:
- самостоятельного результата работы;
- документа;
- markdown/text/table output;
- результата, который можно скачать, передать или использовать дальше.

### Job
Используется для:
- повторяемого процесса;
- расписания;
- подписок;
- доставки;
- operational automation.

### Run
Используется для:
- истории запусков;
- статуса исполнения;
- отладки;
- подтверждения результата.

### Handoff
Используется для:
- передачи результата в рабочий процесс;
- продолжения вне чата;
- подготовки интеграционного следующего шага.

### Policy / Admin layer
Используется для:
- правил источников;
- operational governance;
- справочников;
- управления пользователями;
- наблюдаемости;
- runtime контроля.

## 7. Supported product scenarios v1

### 7.1 Повседневный chat-assisted workflow
Пользователь:
- задаёт вопрос;
- получает ответ;
- прикладывает контекст;
- продолжает диалог;
- при необходимости переводит результат в другой контур.

### 7.2 Chat + files
Пользователь:
- загружает файл;
- или переиспользует файл из профиля;
- получает результат на основе файла;
- может использовать этот результат дальше.

### 7.3 Recurring jobs
Пользователь или владелец процесса:
- создаёт задачу;
- задаёт расписание;
- запускает вручную при необходимости;
- управляет подписками;
- получает историю запусков и результаты.

### 7.4 Monitoring / digest / audit workflows
Система:
- регулярно собирает данные;
- формирует digest / review / audit / triage output;
- доставляет результат;
- позволяет оператору разбирать отклонения.

### 7.5 Assistant for calculations and structured outputs
Чат-помощник:
- собирает данные;
- считает модели и расчёты;
- формирует таблицы;
- выдаёт структурированные результаты, пригодные для использования.

### 7.6 File generation
Система:
- генерирует итоговые файлы;
- позволяет скачать и использовать их дальше;
- не ограничивается ответом в сообщении.

### 7.7 Admin / operational workflows
Admin:
- управляет пользователями;
- смотрит health и events;
- контролирует jobs;
- управляет policy и reference data.

### 7.8 Работа с КП
Система должна поддерживать формирование коммерческих предложений как отдельный прикладной сценарий.

В этот сценарий входят:
- сбор входных данных и контекста;
- структурирование предложения;
- подготовка текста КП;
- генерация итогового документа или артефакта для передачи дальше.

### 7.9 Работа с ТЗ
Система должна поддерживать контур работы с ТЗ как один из ключевых прикладных сценариев.

В этот сценарий входят:
- бизнес-анализ исходного запроса;
- формирование артефактов по требованиям;
- подготовка документов на разработку;
- потенциально — переход к созданию кода, если это уместно в рамках supported path.

### 7.10 Работа с почтой и внутренними системами
Система должна уметь работать не только как чат, но и как операционный слой вокруг коммуникаций и внутренних инструментов.

В этот сценарий входят:
- подготовка материалов для почты;
- обработка входящих рабочих сигналов;
- взаимодействие с внутренними системами;
- handoff результатов и задач в дальнейший рабочий контур.

## 8. Guarded scenarios

Это сценарии, которые допустимы, но должны идти с guardrails, а не как полностью свободный режим.

Сюда входят:
- нестандартные multi-step запросы;
- смешанные source scenarios;
- сложная обработка файлов с неоднозначным ожиданием;
- задачи, где пользователь не понимает, нужен ли ему ответ, job, artifact или handoff;
- partially degraded outcomes.

Правило:
если сценарий выходит за supported core, система не должна делать вид, что это normal path. Она должна переключаться в controlled mode:
- constrained execution;
- guided clarification;
- fallback;
- handoff.

## 9. Non-core / не приоритетно на текущем этапе

Вне текущего ядра:
- dashboards-first product;
- попытка быть универсальным conversational ассистентом лучше корпоративного LLM-чата;
- no-code workflow builder общего назначения внутри Hermes;
- тяжёлая визуальная аналитика как главный драйвер roadmap.

Это не запрещённые направления, но не ядро ближайшего цикла развития.

## 10. Критерии зрелости продукта

Hermes можно считать продуктом, когда одновременно выполняются условия:

1. Есть ясный supported scope.
2. Основные recurring scenarios работают стабильно.
3. Нестандартные сценарии деградируют управляемо.
4. Пользователь понимает разницу между chat / file / artifact / job / handoff.
5. Результат можно использовать дальше без дополнительной ручной расшифровки.
6. У операторов есть наблюдаемость и контроль качества.

## 11. Главные продуктовые риски

### Риск 1. Сползание в «ещё один LLM-чат»
Если roadmap будет крутиться вокруг conversational polish, Hermes потеряет отстройку и стратегическую роль.

### Риск 2. Слишком ранняя переинвестиция в dashboards
Красивый visual layer может съесть ресурс раньше, чем стабилизированы recurring workflows и file contour.

### Риск 3. Неразведённые сущности
Если пользователь не понимает, где у него сообщение, где job, где artifact, а где файл, продукт будет ощущаться как каша.

### Риск 4. Слабая управляемость нестандартных сценариев
Если не ввести controlled degradation, продукт будет нестабилен именно там, где от него ждут гибкости.

### Риск 5. Files останутся второстепенной функцией
Если file contour не станет first-class слоем, Hermes потеряет большую часть прикладной полезности.

## 12. Дальнейшие шаги

### Этап 1. Закрепить product contract
Нужно явно зафиксировать:
- supported scenarios;
- guarded scenarios;
- non-core scenarios;
- expected result по каждому core path.

Результат этапа:
единый продуктовый контракт без расползания по интерпретациям.

### Этап 2. Довести recurring core
Фокус:
- jobs;
- runs;
- subscriptions;
- result delivery;
- recurring monitoring outputs;
- operational stability.

Результат этапа:
Hermes начинает восприниматься как рабочий инструмент автоматизации, а не как просто расширенный чат.

### Этап 3. Довести assistant layer
Фокус:
- information gathering;
- calculations and models;
- table generation;
- structured outputs;
- перевод разговора в artifact / job / handoff.

Результат этапа:
чат-помощник становится реально прикладным инструментом, а не только conversational surface.

### Этап 4. Довести file contour
Фокус:
- intake;
- extraction;
- generation;
- preview;
- reusable file workflows;
- file lifecycle.

Результат этапа:
файлы становятся самостоятельной полезной частью продукта.

### Этап 5. Оформить три обязательных прикладных контура
Фокус:
- формирование КП;
- работа с ТЗ: бизнес-анализ, артефакты, документы на разработку, потенциально код;
- работа с почтой и внутренними системами.

Результат этапа:
Hermes получает не абстрактные capability-классы, а конкретные бизнес-полезные product paths, которые можно внедрять в компании.

### Этап 6. Построить workflow layer поверх core
Фокус:
- связывание chat / files / artifacts / jobs / handoff;
- переход от разовых действий к устойчивым рабочим цепочкам;
- workflow patterns для регулярных и прикладных сценариев.

Результат этапа:
Hermes превращается из набора сильных функций в более цельный рабочий orchestration layer.

### Этап 7. Оставить dashboards производным слоем
Фокус:
- строить дашборды только поверх уже полезных данных, monitoring и recurring outputs;
- не тащить продукт в dashboard-first модель.

Результат этапа:
visual layer усиливает продукт, а не подменяет его смысл.

## 13. Практический roadmap верхнего уровня

### Ближайший цикл
- product contract по recurring / assistant / files;
- жёсткое разведение core entities;
- acceptance по recurring jobs и monitoring;
- user-facing states для run/result/error/degraded outcome.

### Следующий цикл
- assistant workflows для research / calculations / tables;
- file generation и file lifecycle;
- handoff patterns в рабочий контур;
- прикладные сценарии для КП и ТЗ.

### Более поздний цикл
- workflow layer поверх recurring / assistant / files;
- интеграция почтовых и внутренних систем в устойчивые product paths;
- dashboard enrichment поверх уже зрелых recurring и analytical outputs;
- более богатые visual summaries там, где они реально повышают полезность.

## 14. Короткая итоговая формулировка

Hermes v1 — это не ещё один корпоративный AI-чат.

Hermes v1 — это внутренний AI-продукт для recurring workflows, monitoring, прикладного assistant-слоя, файлов, артефактов и операционного handoff.

Именно в этой роли он должен развиваться и позиционироваться внутри компании.
