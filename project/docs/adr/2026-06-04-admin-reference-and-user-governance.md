# ADR-2026-06-04 — Local-first admin governance для пользователей и справочников

Статус: принято
Дата: 2026-06-04

## 1. Контекст

В `hermes-web-mvp` уже существовали:
- backend как operational-слой web-приложения;
- frontend как отдельный UI;
- Hermes API Server как внутренний агентный runtime.

Но admin-контур оставался незавершённым:
- часть прикладных справочников жила как frontend hardcode;
- ручное управление пользователями было неполным;
- история изменений admin-сущностей отсутствовала или была недостаточно явной;
- versioning для ключевых правок не был закреплён как обязательная часть модели;
- документация не фиксировала это как сознательное архитектурное решение.

Пользовательский запрос был не на «черновую заготовку», а на рабочий local-first контур:
- всё должно работать end-to-end;
- на фронте пользовательские подписи должны быть на русском;
- нужны логирование изменений и версионность;
- нельзя плодить внешний сервис или второй master-контур без реальной необходимости.

## 2. Проблема

Если оставить старую схему, появляются типовые риски:
- frontend начинает хранить бизнес-истину о справочниках;
- админ не может полноценно управлять пользователями вручную;
- изменения сложно объяснить, проверить и расследовать;
- product-like управление подменяется правками кода и seed-данных;
- со временем система получает две правды: в UI/коде и в backend/БД.

Для local-first многопользовательского web-приложения это плохая траектория: она снижает управляемость сильнее, чем экономит время на старте.

## 3. Решение

Принято следующее архитектурное решение.

### 3.1 Backend остаётся operational source of truth для web users и reference data

Канонический слой для этих сущностей — backend DB, а не frontend и не внешняя система.

Это касается:
- пользователей web-приложения;
- профиля и настроек пользователя;
- прикладных справочников, используемых frontend и admin UI.

### 3.2 Справочники переводятся в универсальную backend-модель

Вместо frontend hardcode вводится backend reference layer:
- `reference_catalogs`
- `reference_items`

Модель справочников:
- `dataset_key` задаёт набор;
- `item_key` задаёт элемент;
- `label` хранит пользовательское имя;
- `payload_json` хранит расширяемые поля;
- `sort_order` и `is_active` управляют поведением UI;
- `version` фиксирует версию элемента;
- timestamps фиксируют жизненный цикл записи.

### 3.3 Ручной admin CRUD по пользователям становится частью базового контура

Пользователь создаётся и администрируется не только через импорт, но и вручную.

Admin должен уметь:
- создать пользователя;
- поменять роль;
- изменить profile-поля;
- поменять ограничения и pinned notes;
- обновить пароль;
- увидеть историю изменений.

Это закрепляет web users как самостоятельную прикладную сущность, а не как побочный артефакт тестового seed.

### 3.4 Для admin-сущностей вводятся audit trail и versioning

Вместо тяжёлого event sourcing выбран practical minimum:
- `users.version`
- `reference_items.version`
- `user_change_log`
- `reference_item_change_log`

Форма аудита:
- append-only log;
- `snapshot_json` после изменения;
- `actor_user_id`;
- `change_type`;
- `created_at`.

Это решение выбрано как достаточно сильное для governance-задач и достаточно дешёвое для MVP.

### 3.5 Frontend получает данные через API и показывает их по-русски

Frontend больше не должен держать business dictionaries как постоянный hardcode.

Его роль:
- отрисовывать то, что пришло из backend;
- давать admin-интерфейс для ручного управления;
- показывать русские подписи, статусы и ошибки как product-facing слой.

### 3.6 История изменений должна быть видна в UI, а не только существовать в БД

Audit без видимой истории в интерфейсе слишком легко превращается в технический долг. Поэтому история по users и reference items выводится в admin UI.

## 4. Почему выбрано именно это решение

### 4.1 Почему не оставили frontend hardcode

Потому что hardcode в UI:
- усложняет администрирование;
- создаёт расхождение между тем, что видит пользователь, и тем, чем владеет backend;
- делает bootstrap и поддержку зависимыми от правки кода.

### 4.2 Почему не вынесли это во внешнюю БД или SaaS

Потому что задача хорошо решается в текущем local-first стеке:
- backend уже существует;
- DuckDB уже используется;
- Hermes уже даёт локальный runtime;
- дополнительная инфраструктура не даёт пропорциональной выгоды на текущем этапе.

### 4.3 Почему не сделали полноценный event sourcing

Потому что для текущей стадии это было бы лишним усложнением. Snapshot-based audit:
- проще внедряется;
- проще проверяется вручную;
- уже закрывает вопрос «кто, когда и во что изменил запись».

### 4.4 Почему versioning обязателен, а не опционален

Потому что timestamps сами по себе не отвечают на вопрос, в какой версии сущность была после конкретного изменения. Для admin-контура `version` — это дешёвый и очень полезный якорь управляемости.

## 5. Последствия решения

### Положительные

- исчезает frontend как скрытый источник справочной истины;
- admin-контур становится реально управляемым;
- появляется прозрачность изменений;
- backend получает единую рабочую модель для users/reference;
- MVP становится заметно ближе к production-like режиму управления.

### Отрицательные и компромиссы

- backend усложняется по сравнению с чисто демо-версией;
- появляются дополнительные таблицы и endpoint-ы;
- нужен контроль SQL-запросов после добавления новых полей вроде `version`;
- audit хранит snapshot, а не компактный diff.

Это приемлемые издержки, потому что они напрямую покупают управляемость и предсказуемость.

## 6. Технические детали реализации

Основной файл реализации:
- `services/backend/app.py`

Основные UI-файлы:
- `services/frontend/index.html`
- `services/frontend/app.js`

Ключевые реализации:
- backend reference datasets через `reference_catalogs` и `reference_items`;
- admin endpoint-ы для users и reference data;
- `user_change_log` и `reference_item_change_log`;
- `version` в `users` и `reference_items`;
- вывод истории в admin UI;
- русские front-facing строки.

## 7. Что было важно проверить на практике

Достаточной проверкой считалось не описание, а реальный прогон:
- login;
- create user;
- update user;
- user history;
- create reference item;
- update reference item;
- reference history;
- рост `version`;
- сохранение profile-полей.

На практике выявились два важных технических урока:

1. После добавления `version` в выборки DuckDB нужно перепроверять все запросы с `GROUP BY`, включая helper-функции, вызываемые после записи.
2. Если `reference_items` сериализуются без `version` в `SELECT`, update может реально сохраниться в БД, но вернуться в ответе со старым значением. Значит, нужно проверять не только запись, но и read-after-write serialization path.

## 8. Что сознательно не решается этим ADR

Этот ADR не закрывает полностью:
- delete/restore lifecycle для users и reference items;
- сложный RBAC;
- explicit identity mapping между web user, Hermes actor и Telegram identity;
- production-grade observability;
- миграцию на более тяжёлую инфраструктуру.

Это следующие, отдельные решения.

## 9. Итоговая формулировка

Для Hermes Web MVP принято считать, что:
- пользователи web-приложения и прикладные справочники живут в backend DB как local-first operational truth;
- frontend не хранит бизнес-истину о справочниках;
- admin обязан иметь ручной CRUD по пользователям и справочникам;
- audit trail и versioning обязательны для admin-сущностей;
- история изменений должна быть доступна не только в БД, но и в UI;
- новые внешние компоненты не вводятся, пока текущий local-first стек закрывает задачу.
