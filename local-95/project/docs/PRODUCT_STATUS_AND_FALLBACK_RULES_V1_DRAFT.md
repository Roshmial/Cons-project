# Product Status & Fallback Rules v1 Draft — Hermes

Дата: 2026-06-24
Статус: draft
Назначение: единые пользовательские статусы и правила деградации для Sprint 0

## 1. Зачем нужен этот документ

Проблема не только в ошибках. Проблема в том, что пользователь должен понимать разницу между:
- задача ещё идёт;
- задача завершилась;
- задача завершилась частично;
- задача не дала сигнала;
- задача реально сломалась;
- задача требует уточнения;
- результат передан дальше.

Если эти состояния не разведены, продукт всегда выглядит сырым, даже когда backend технически работает.

## 2. Базовый набор статусов

### running
Смысл:
- система приняла задачу и исполняет её.

Показывать пользователю:
- что задача в работе;
- если возможно — какой это тип процесса: ответ, запуск, обработка файла.

Следующее допустимое действие:
- ждать;
- обновить статус;
- при необходимости перейти к run/job detail.

Нельзя интерпретировать как:
- completed;
- failed.

### completed
Смысл:
- сценарий завершён штатно и результат готов к использованию.

Показывать пользователю:
- краткий итог;
- доступ к результату;
- следующий полезный шаг: открыть, скачать, сохранить, использовать дальше.

Следующее допустимое действие:
- читать результат;
- скачивать/открывать;
- при необходимости сохранять как artifact/job.

### completed_with_limitations
Смысл:
- сценарий завершился, но не в полном объёме.

Использовать, когда:
- часть входных данных не обработана;
- часть источников недоступна;
- результат частичный;
- extraction неполный;
- output сформирован с оговорками.

Показывать пользователю:
- что результат частичный;
- что именно ограничено;
- можно ли им пользоваться дальше.

Следующее допустимое действие:
- использовать частичный результат;
- доуточнить;
- повторить позже;
- передать оператору.

Нельзя интерпретировать как:
- обычный success;
- outright failure.

### failed
Смысл:
- сценарий не был выполнен.

Использовать, когда:
- задача не стартовала или упала;
- файл не обработан;
- recurring run завершился ошибкой;
- действие не применилось.

Показывать пользователю:
- что не удалось;
- по какой категории причина;
- что делать дальше: retry, inspect, уточнить, handoff.

Нельзя смешивать с:
- empty_result;
- completed_with_limitations.

### empty_result
Смысл:
- система сработала штатно, но полезного сигнала не нашла.

Использовать, когда:
- мониторинг не нашёл событий;
- digest-подборка пустая по условиям;
- поиск не дал результата при корректной работе контура.

Показывать пользователю:
- что система отработала нормально;
- что просто ничего релевантного не найдено.

Нельзя трактовать как:
- error;
- degraded;
- тишину без объяснения.

### needs_clarification
Смысл:
- система не должна продолжать без дополнительного уточнения.

Использовать, когда:
- запрос неоднозначен;
- не хватает критичного входа для расчёта;
- непонятно, нужен ответ, job, artifact или handoff;
- неясен желаемый формат результата.

Показывать пользователю:
- какое уточнение нужно;
- почему без него результат будет ненадёжным.

Нельзя использовать как:
- замену нормального fallback там, где система и так может сделать поддерживаемую часть работы.

### handed_off
Смысл:
- результат подготовлен и передан в следующий рабочий контур.

Использовать, когда:
- передача действительно произошла;
- есть понятная фиксация факта handoff.

Показывать пользователю:
- куда передано;
- что именно передано;
- что теперь следующий контур должен с этим делать.

Нельзя использовать как:
- предположение;
- красивую формулировку без фактической передачи.

## 3. Правила fallback

### Правило 1. Не делать вид, что любой сценарий normal path
Если задача выходит за supported core, система должна переключиться в один из контролируемых режимов:
- completed_with_limitations;
- needs_clarification;
- failed;
- handed_off.

### Правило 2. Empty result — это не ошибка
Это особенно важно для recurring monitoring, digest, triage и search-like сценариев.

### Правило 3. Partial result должен быть явно помечен
Нельзя выдавать частичный output как полный.

### Правило 4. Clarification — только когда без него реально нельзя
Не превращать каждую неидеальную ситуацию в бесконечные уточнения.

### Правило 5. Handoff требует подтверждения
Если результат только подготовлен, но ещё не передан, это не `handed_off`.

## 4. Рекомендуемые пользовательские формулировки

### running
- Выполняется
- Задача запущена
- Идёт обработка

### completed
- Завершено
- Результат готов

### completed_with_limitations
- Завершено с ограничениями
- Результат частичный

### failed
- Не удалось выполнить
- Задача завершилась ошибкой

### empty_result
- Ничего не найдено
- Сигналов не обнаружено

### needs_clarification
- Нужно уточнение
- Недостаточно данных для надёжного результата

### handed_off
- Передано дальше
- Результат направлен в следующий контур

## 5. Минимальная матрица применения

| Контур | running | completed | completed_with_limitations | failed | empty_result | needs_clarification | handed_off |
|---|---|---|---|---|---|---|---|
| Chat answer | Да | Да | Да | Да | Редко | Да | Guarded |
| Job / run | Да | Да | Да | Да | Да | Редко | Guarded |
| Monitoring | Да | Да | Да | Да | Да | Редко | Guarded |
| File processing | Да | Да | Да | Да | Нетипично | Да | Нет |
| Artifact preparation | Да | Да | Да | Да | Нетипично | Да | Guarded |

## 6. Что нужно сделать после этого draft

Следующие шаги Sprint 0:
- сопоставить эти статусы с текущими backend responses;
- сопоставить их с текущим UI copy;
- убрать места, где `failed`, `empty_result` и `completed_with_limitations` смешиваются;
- в recurring core обеспечить явный status/result path.

## 7. Короткий итог

Этот draft задаёт минимальную status-модель Hermes:
- она достаточна, чтобы перестать путать ошибку, частичный результат, пустой результат и необходимость уточнения;
- она создаёт базу для продуктового cleanup recurring / assistant / file contour в следующих шагах Sprint 0.
