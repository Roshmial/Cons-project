# Пользовательский сценарий тестирования Hermes Web MVP

## 1. Для кого этот сценарий

Этот сценарий предназначен для человека, который впервые видит систему и тестирует её как обычный пользователь, не администратор.

Сценарий специально не требует знания внутренней архитектуры, API и админских экранов.

## 2. Цель проверки

Нужно убедиться, что обычный пользователь может:
- войти в систему;
- понять, куда он попал;
- открыть и вести чат;
- приложить файл;
- выбрать режим работы с источниками;
- получить ответ;
- увидеть историю;
- при необходимости обновить профиль.

## 3. Что должно быть готово заранее

Перед началом теста должны быть уже подняты:
- frontend `http://127.0.0.1:8793`
- backend `http://127.0.0.1:8791`
- CopilotKit runtime `http://127.0.0.1:8794`
- Hermes API Server

Также должен быть подготовлен обычный пользователь с валидным логином и паролем.

Важно: этот сценарий не предполагает admin-доступ и не требует входа под администратором.

## 4. Базовый маршрут пользователя

### Шаг 1. Открытие системы

Действие:
- открыть `http://127.0.0.1:8793`

Ожидаемый результат:
- страница открывается без ошибки браузера;
- пользователь видит экран входа или сразу свою рабочую область, если сессия уже восстановлена.

Что считается ошибкой:
- белый экран;
- ошибка соединения;
- бесконечная загрузка без перехода к экрану входа или рабочего пространства.

### Шаг 2. Вход

Действие:
- ввести логин и пароль обычного пользователя;
- нажать вход.

Ожидаемый результат:
- вход проходит успешно;
- пользователь попадает в основное рабочее пространство;
- после обновления страницы сессия не теряется сразу.

Что считается ошибкой:
- корректные учётные данные не принимаются;
- после входа интерфейс ломается;
- после reload пользователь сразу выбрасывается без причины.

### Шаг 3. Первичное понимание интерфейса

Действие:
- осмотреть главный экран без админских действий.

Ожидаемый результат:
- понятно, где список чатов;
- понятно, где поле ввода;
- понятно, как открыть профиль;
- нет лишних админских блоков и непонятных технических настроек.

Что считается ошибкой:
- интерфейс перегружен техническими элементами;
- пользователь видит управление источниками, которое относится к администратору;
- сложно понять, как вообще начать диалог.

### Шаг 4. Создание нового чата

Действие:
- создать новый чат;
- открыть его.

Ожидаемый результат:
- новый чат появляется в списке;
- чат открывается;
- поле ввода готово к работе.

Что считается ошибкой:
- чат не создаётся;
- чат создаётся, но не открывается;
- после создания интерфейс сбрасывается в непонятное состояние.

### Шаг 5. Обычный вопрос без файлов

Действие:
- отправить обычный текстовый вопрос, например рабочий вопрос по ИТ или задаче.

Ожидаемый результат:
- сообщение пользователя появляется в истории;
- система показывает ответ;
- ответ связан именно с этим чатом;
- после обновления страницы история остаётся.

Что считается ошибкой:
- сообщение исчезает;
- ответ не приходит без объяснения;
- история не сохраняется.

### Шаг 6. Проверка режима работы с источниками

Действие:
- найти в чате блок выбора режима работы с источниками;
- последовательно посмотреть доступные режимы.

Ожидаемый результат:
- пользователь видит только 3 режима:
  - `local_only`
  - `local_first`
  - `global_only`
- пользователь не видит ручного выбора реестра источников и не настраивает коннекторы сам.

Что считается ошибкой:
- в чате доступны лишние глобальные переключатели;
- пользователь может менять состав inventory;
- в чате появляются внутренние technical keys и admin-level настройки.

### Шаг 7. Запрос с разными режимами

Действие:
- задать один и тот же прикладной вопрос в разных режимах;
- проверить, что переключение режима не ломает сценарий общения.

Ожидаемый результат:
- сообщение уходит корректно;
- чат не ломается;
- история сохраняется;
- режим воспринимается как прикладная настройка, а не как техническая конфигурация.

Что считается ошибкой:
- при смене режима интерфейс перестаёт отправлять сообщение;
- пользователь получает техническую ошибку вместо ответа;
- выбранный режим не сохраняется в рамках текущего ввода.

### Шаг 8. Запрос с файлом

Действие:
- прикрепить файл;
- отправить запрос на анализ файла.

Ожидаемый результат:
- файл прикрепляется;
- сообщение уходит;
- в истории видно, что пользователь работал с вложением;
- чат не требует от пользователя отдельного выбора глобального режима только потому, что приложен файл.

Что считается ошибкой:
- файл не прикрепляется;
- прикрепление ломает отправку;
- пользователь вынужден разбираться с admin-level классификацией источников.

### Шаг 9. Проверка профиля

Действие:
- открыть профиль;
- изменить одно безопасное поле, например описание стиля или команду;
- сохранить.

Ожидаемый результат:
- профиль сохраняется;
- после обновления страницы изменения остаются;
- пользователь не видит лишние административные поля.

Что считается ошибкой:
- данные не сохраняются;
- после reload всё пропадает;
- профиль смешивает пользовательские и административные настройки.

### Шаг 10. Проверка возврата в чат

Действие:
- уйти из чата в другой раздел;
- вернуться обратно.

Ожидаемый результат:
- активный чат можно снова открыть;
- история остаётся;
- интерфейс не теряет контекст.

Что считается ошибкой:
- при возврате чат пустой;
- выбранный чат теряется;
- интерфейс как будто начинает с нуля.

## 5. Дополнительный сценарий для dashboard-запроса

### Шаг 11. Запрос на построение dashboard

Действие:
- в чате попросить построить dashboard по доступным данным.

Ожидаемый результат:
- если данных недостаточно, система корректно уточняет условия;
- если данных достаточно, система может вернуть dashboard-результат;
- пользователь не должен разбираться в реестре внутренних коннекторов.

Что считается ошибкой:
- система сразу перекладывает на пользователя admin-задачу выбора коннекторов;
- в ответах появляются сырые технические поля вместо понятного диалога.

## 6. Что должно быть отдельно проверено тестировщиком

Тестировщик должен отдельно отметить:
- понятен ли интерфейс человеку без контекста проекта;
- не выглядит ли экран чата перегруженным;
- не просачиваются ли в пользовательский слой административные сущности;
- достаточно ли ясно, что пользователь выбирает только режим, а не саму архитектуру данных.

## 7. Критерии приёмки для роли user

Система считается приемлемой для обычного пользователя, если:
- вход и восстановление сессии работают;
- можно создать и вести чат;
- можно приложить файл;
- история сообщений сохраняется;
- профиль сохраняется;
- в чате есть только 3 пользовательских режима;
- в чате нет admin-level управления inventory и коннекторами;
- интерфейс понятен без объяснения внутренней архитектуры.
