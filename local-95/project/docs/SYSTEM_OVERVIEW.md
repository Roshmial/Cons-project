# Hermes Web MVP — полное описание системы

## 1. Назначение системы

Hermes Web MVP — это local-first web-слой вокруг Hermes Agent, который даёт:
- chat-first интерфейс для пользователя;
- отдельный backend для хранения состояния, пользователей, чатов, задач и справочников;
- отдельный runtime для CopilotKit;
- управляемую модель источников данных и маршрутизации запросов.

Система не строится как thin frontend поверх внешнего SaaS. Основная логика остаётся в локальном контуре пользователя или команды.

## 2. Архитектурный принцип

Главный принцип — local-first, но не local-only.

Это означает:
- по умолчанию система предпочитает локальные данные, локальные файлы, локальный state и локальный runtime;
- при необходимости она может использовать внешний обзор или внешние API, если это разрешено policy;
- browser не ходит в Hermes напрямую;
- backend является единственной точкой консолидации пользовательского состояния и orchestration на уровне приложения.

## 3. Канонический runtime-контур

Канонические порты:
- `8793` — frontend;
- `8791` — backend;
- `8794` — CopilotKit runtime;
- `8642/v1` — Hermes API Server.

Канонический поток запроса:
1. пользователь открывает frontend;
2. frontend работает с backend API;
3. backend проверяет сессию, профиль, историю, policy и данные;
4. backend при необходимости вызывает Hermes API Server;
5. backend сохраняет результат в app-store;
6. frontend показывает результат пользователю.

## 4. Основные компоненты

### 4.1 Frontend React

Назначение:
- экран логина;
- чаты;
- профиль;
- задачи;
- админка;
- отображение dashboard-артефактов и policy UI.

Основные файлы:
- `services/frontend-react/src/App.jsx`
- `services/frontend-react/src/api.js`
- `services/frontend-react/src/styles.css`

### 4.2 Backend API

Назначение:
- auth и session management;
- хранение пользователей, тредов, сообщений, файлов и задач;
- сбор bootstrap-пакета для frontend;
- admin endpoints;
- policy endpoints;
- интеграция с Hermes API Server.

Основной файл:
- `services/backend/app.py`

### 4.3 CopilotKit runtime

Назначение:
- runtime для CopilotKit-сценариев внутри web-контура;
- отдельный вспомогательный runtime, не заменяющий backend.

Точка запуска:
- `run_copilotkit_runtime_service.sh`
- `scripts/copilotkit_runtime_8794.cjs`

### 4.4 DuckDB app-store

Основное operational-хранилище:
- `services/backend/data/hermes_web_app.duckdb`

Что хранится:
- пользователи;
- сессии;
- чаты и сообщения;
- файлы;
- задачи и их ACL/подписки;
- справочники и элементы справочников;
- аудит изменений.

## 5. Роли в системе

### 5.1 Пользователь

Может:
- входить в систему;
- открывать и создавать чаты;
- редактировать профиль;
- работать с файлами;
- запускать обычные chat-сценарии;
- выбирать режим работы с источниками в рамках трёх режимов;
- использовать доступные задачи и подписки.

Не может:
- менять глобальную policy источников;
- определять состав inventory;
- менять классификацию internal/external;
- работать с административными сущностями.

### 5.2 Администратор

Может:
- управлять пользователями;
- управлять справочниками;
- просматривать health/operations;
- задавать объявление в чате;
- задавать глобальную policy источников;
- определять принадлежность коннектора к внутреннему или внешнему контуру.

## 6. Модель данных и навигации

### 6.1 Пользователи

Пользователь имеет:
- базовый профиль;
- assistant profile;
- рабочие настройки;
- ограничения;
- роль;
- версионность.

### 6.2 Чаты и сообщения

Модель строится вокруг:
- `user_id`
- `threads`
- `messages`

Это важнее session-centric summary-модели. История разговора хранится как реальные треды и сообщения.

### 6.3 Файлы

Поддерживаются:
- пользовательские вложения;
- повторное использование уже загруженных файлов;
- assistant-generated attachments.

### 6.4 Справочники

Справочники хранят:
- reference catalogs;
- reference items;
- payload;
- историю изменений.

Справочники используются как backend-source-of-truth для многих UI-списков и policy-настроек.

## 7. Модель источников данных

### 7.1 Верхний уровень

Верхнеуровневые источники в текущей модели:
- `user_attachment_dataset`
- `local_dataset_registry`
- `internal_connector`
- `external_connector`
- `web_research`

### 7.2 Дочерние коннекторы

У групп `internal_connector` и `external_connector` есть дочерние коннекторы, например:
- `hermes_api`
- `copilotkit_runtime`
- `telegram_analytics_workspace`
- `telegram_api`
- `google_api`
- `public_procurement_api`

### 7.3 Кто управляет чем

Пользователь в чате:
- выбирает только режим обработки запроса.

Администратор:
- управляет разрешёнными верхнеуровневыми источниками;
- управляет включением коннекторов;
- управляет классификацией коннекторов по контурам.

## 8. Policy-модель

### 8.1 Пользовательские режимы

Поддерживаются только три режима:
- `local_only`
- `local_first`
- `global_only`

### 8.2 Что не является отдельным режимом

Не нужно вводить отдельные глобальные режимы вроде:
- `link_only`
- `file_only`
- `dataset_only`

Если пользователь дал:
- конкретный файл;
- конкретную ссылку;
- конкретный dataset;
- конкретный connector,

это трактуется как explicit source override на уровне конкретного запроса.

### 8.3 Приоритеты

Практическая логика приоритета такая:
- explicit source в самом запросе;
- request-level override;
- admin policy default.

### 8.4 Internal vs external

Классификация internal/external относится к admin layer.

Она не должна превращаться в отдельный пользовательский переключатель в чате.

## 9. Что изменено в текущем цикле работ

### 9.1 Chat UI

В чате оставлена только настройка режима:
- `local_only`
- `local_first`
- `global_only`

Из чата убрано ручное управление:
- верхнеуровневыми источниками;
- дочерними коннекторами.

### 9.2 Admin UI

В админке добавлены или усилены:
- понятные русские тексты для policy-блока;
- отдельный блок глобальных правил;
- блок разрешённых источников;
- блок внутренних и внешних коннекторов;
- блок явной классификации коннекторов по контурам.

### 9.3 Backend

В backend добавлена поддержка `connector_group_overrides`, чтобы админская классификация не зависела только от discovery и могла переопределять inventory.

## 10. Проверки и текущее подтверждение

Подтверждено:
- backend компилируется;
- frontend собирается;
- backend smoke-тесты проходят (`7 tests, OK`);
- login в live backend работает;
- admin policy read/patch/read работает;
- живой перенос коннектора между `internal_connector` и `external_connector` работает и виден в `bootstrap.data_sources`.

## 11. Эксплуатационные ограничения текущего состояния

Это ещё MVP, а не production-платформа корпоративного класса.

Что уже хорошо:
- контур разделён;
- browser не знает секретов Hermes;
- backend — единая точка состояния;
- policy и inventory живут в приложении, а не размазаны по frontend.

Что может потребоваться позже:
- reverse proxy;
- внешний мониторинг;
- формальная backup-стратегия;
- production DB и миграции более строгого уровня;
- отдельные профили и секреты для нескольких инсталляций.
