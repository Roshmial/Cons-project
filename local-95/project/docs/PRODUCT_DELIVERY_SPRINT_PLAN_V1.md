# Product Delivery Sprint Plan v1 — Hermes

Дата: 2026-06-24
Статус: рабочий спринтовый план
Основа: PRODUCT_CORE_DEFINITION_V1.md
Горизонт: 6 спринтов
Рекомендуемая длительность спринта: 2 недели

## 1. Цель плана

Этот план нужен, чтобы перевести Hermes из состояния «уже много чего умеет» в состояние «понятный внутренний продукт с предсказуемым ядром».

Главный принцип плана:
- не распыляться по всем направлениям сразу;
- сначала довести recurring core;
- затем усилить assistant и file contour;
- потом оформить прикладные сценарии;
- только после этого собирать workflow layer;
- dashboards держать производным слоем.

## 2. Что уже считаем базой

По текущему контуру уже есть:
- живой recurring / cron / monitoring слой;
- jobs и run history на уровне рабочего контура;
- чат как точка входа;
- базовая работа с файлами;
- admin / operational слой;
- начальная продуктовая рамка в `PRODUCT_CORE_DEFINITION_V1.md`.

Это значит, что план не про «создать продукт с нуля», а про доведение существующего ядра до рабочего продуктового состояния.

## 3. Общая логика приоритизации

Приоритеты развития:
1. recurring / cron / monitoring;
2. assistant layer;
3. file contour;
4. прикладные сценарии: КП, ТЗ, почта / внутренние системы;
5. workflow layer;
6. dashboards как производный слой.

## 4. Формат спринтов

Для каждого спринта задаются:
- цель;
- что именно дорабатываем;
- какой результат считаем done;
- какие риски держим под контролем.

## 5. Спринт 0 — фиксация контракта и границ продукта

Текущий draft Sprint 0 уже оформлен в документах:
- `PRODUCT_CONTRACT_ACCEPTANCE_MATRIX_V1_DRAFT.md`
- `PRODUCT_ENTITY_GLOSSARY_V1_DRAFT.md`
- `PRODUCT_STATUS_AND_FALLBACK_RULES_V1_DRAFT.md`


### Цель
Снять расплывчатость и зафиксировать, что Hermes уже обещает как продукт, а что пока нет.

### Что дорабатывать
1. Сделать `Product Contract / Acceptance Matrix` по трём core-блокам:
   - recurring;
   - assistant;
   - files.
2. Для каждого блока зафиксировать:
   - supported scenarios;
   - guarded scenarios;
   - unsupported / non-core scenarios;
   - expected result;
   - acceptable fallback.
3. Жёстко развести продуктовые сущности:
   - chat;
   - file;
   - artifact;
   - job;
   - run;
   - handoff.
4. Для каждого core path описать user-facing статусы:
   - running;
   - completed;
   - error;
   - degraded;
   - partial result.

### Done
- есть отдельный документ с acceptance matrix;
- есть draft словаря сущностей;
- есть draft правил статусов и fallback;
- по основным сценариям больше нет двусмысленности, что считать нормальным результатом;
- сущности разведены хотя бы на уровне продукта и UX-терминологии;
- backend начал возвращать normalized run semantics и message surface semantics;
- frontend использует public statuses для jobs/runs и surface labels для chat messages;
- добавлен implementation baseline документ `SPRINT0_IMPLEMENTATION_BASELINE_2026-06-24.md`.

### Почему это первым
Без этого следующие спринты будут серией локальных улучшений без общего продуктового контракта.

## 6. Спринт 1 — доведение recurring core

Связанный implementation backlog:
- `docs/plans/2026-06-24-sprint1-recurring-core-implementation-backlog.md`


### Цель
Сделать recurring / cron / monitoring ядро не просто рабочим, а устойчивым и продуктово понятным.

### Что дорабатывать
1. Jobs UX:
   - список задач;
   - детали задачи;
   - run history;
   - текущий статус;
   - подписки;
   - результат последнего запуска.
2. Run/result states:
   - явные состояния success / error / degraded / empty output;
   - читаемые причины ошибок;
   - понятная разница между «задача не сработала» и «сработала, но не нашла сигналов».
3. Monitoring output contract:
   - единый паттерн для digest / audit / triage / recurring reviews;
   - единый способ читать результат.
4. Operational stability:
   - разобрать красные jobs;
   - убрать очевидные recurring failure points;
   - добавить контроль stuck/pending cases там, где он ещё слабый.

### Done
- recurring jobs выглядят как first-class продуктовая функция;
- по каждому запуску понятны статус, результат и ошибка;
- monitoring-сценарии можно уже уверенно показывать как главное преимущество Hermes.

### Что это даёт бизнесу
Hermes перестаёт быть «умным чатом с cron где-то сбоку» и становится рабочим automation-инструментом.

## 7. Спринт 2 — доведение assistant layer

### Цель
Сделать чат-помощник действительно полезным прикладным инструментом, а не просто general chat surface.

### Что дорабатывать
1. Сценарии assistant core:
   - сбор информации;
   - прикладной research;
   - расчёты и модели;
   - таблицы;
   - structured outputs.
2. Выходы assistant layer:
   - ответ в чат;
   - таблица;
   - structured result;
   - artifact;
   - перевод в job / handoff.
3. UX для выбора результата:
   - просто ответить;
   - оформить результат;
   - сохранить как задачу;
   - передать дальше.
4. Quality control:
   - acceptance на research / calculations / tables;
   - явные fallback-состояния, если задача неоднозначна.

### Done
- assistant layer стабильно решает повседневные прикладные задачи;
- пользователь понимает, когда он получает просто ответ, а когда продуктовый результат;
- assistant можно использовать как отдельную 2-ю линию ценности продукта.

### Риск
Если не сделать этот спринт после recurring core, чат будет восприниматься как недоделанный конкурент корпоративному LLM-чату.

## 8. Спринт 3 — доведение file contour

### Цель
Превратить файлы из вспомогательной функции в отдельный полезный продуктовый слой.

### Что дорабатывать
1. File lifecycle:
   - загружен;
   - распознан;
   - не распознан;
   - использован в ответе;
   - сохранён для повторного использования;
   - сгенерирован как результат.
2. Preview:
   - улучшить встроенный preview для текстовых и табличных форматов;
   - объяснять, что именно система извлекла из файла.
3. Reuse:
   - сделать выбор файлов из профиля более понятным;
   - показать, какие файлы реально были использованы в конкретной задаче.
4. Generation:
   - привести generated files к понятному deliverable path;
   - развести attachment / export / artifact / file result.
5. Acceptance по форматам:
   - txt;
   - csv;
   - pdf-text;
   - docx;
   - xlsx.

### Done
- файл становится понятной рабочей сущностью;
- generated files и input files не смешиваются в голове пользователя;
- file contour можно использовать в реальных business-path задачах.

### Что это даёт
Без этого Hermes теряет значимую часть прикладной полезности для ТЗ, КП и document-heavy сценариев.

## 9. Спринт 4 — оформление трёх прикладных контуров

### Цель
Сделать не абстрактные capabilities, а три конкретных внедряемых сценария.

### 9.1 Контур КП
Что дорабатывать:
- intake нужных данных;
- шаблон структуры КП;
- правила сборки предложения;
- выпуск итогового документа / артефакта.

Done:
- есть повторяемый путь «входные данные -> draft КП -> итоговый документ».

### 9.2 Контур ТЗ
Что дорабатывать:
- intake исходного запроса;
- бизнес-анализ;
- структура ТЗ;
- артефакты для разработки;
- при необходимости переход к code-oriented output.

Done:
- есть повторяемый путь «запрос -> анализ -> ТЗ -> dev-ready artifact».

### 9.3 Контур почты и внутренних систем
Что дорабатывать:
- подготовка писем / ответов / служебных материалов;
- обработка входящих рабочих сигналов;
- подготовка handoff в дальнейший контур;
- первичные паттерны интеграции с внутренними системами.

Done:
- есть хотя бы базовый устойчивый path для почтово-операционных сценариев.

### Общий результат спринта
Hermes получает три понятных product path, которые можно показывать компании не как «возможности модели», а как полезные рабочие маршруты.

## 10. Спринт 5 — workflow layer поверх core

### Цель
Связать уже стабилизированные слои в цельные рабочие цепочки.

### Что дорабатывать
1. Workflow patterns:
   - chat -> file -> artifact;
   - chat -> assistant result -> job;
   - monitoring -> triage -> handoff;
   - input request -> analysis -> document -> delivery.
2. Переходы между сущностями:
   - из чата в задачу;
   - из файла в анализ;
   - из результата в артефакт;
   - из артефакта в handoff.
3. Product states:
   - где пользователь находится в процессе;
   - какой следующий допустимый шаг;
   - что уже завершено.

### Done
- появляется не набор сильных экранов, а связный orchestration layer;
- Hermes начинает выглядеть как единая рабочая система.

### Важное ограничение
Этот спринт нельзя ставить раньше, чем стабилизированы recurring, assistant и files. Иначе workflow layer просто зацементирует сырость нижележащих контуров.

## 11. Спринт 6 — dashboards как усилитель, а не как центр продукта

### Цель
Использовать dashboards там, где они реально усиливают уже полезные результаты.

### Что дорабатывать
1. Dashboard outputs только для зрелых сценариев:
   - recurring monitoring;
   - recurring analytics;
   - summary-heavy outputs.
2. Визуализация должна быть вторичной к смыслу:
   - сначала useful output;
   - потом visual enrichment.
3. Не строить dashboard-first UX.

### Done
- dashboards усиливают recurring и analytical outputs;
- продукт не превращается в витрину без операционного ядра.

## 12. Что делать в первую очередь

Если нужен короткий ответ «что дорабатывать прямо сейчас», то порядок такой:

### Сначала
1. Product Contract / Acceptance Matrix
2. Recurring core UX и stability
3. Run/result/error/degraded states

### Потом
4. Assistant workflows
5. File lifecycle и generated files
6. Разведение artifact / file / export / attachment

### После этого
7. КП и ТЗ как отдельные product paths
8. Почта и внутренние системы
9. Workflow layer

### В самом конце
10. Dashboards как усиление, а не как база

## 13. Управленческий смысл плана

План решает сразу три проблемы:

1. Не даёт продукту расползтись
Потому что фиксирует, что важнее recurring core, чем красивые вторичные слои.

2. Не ставит chatbot-гонку в центр
Потому что Hermes должен выигрывать не качеством «болтовни», а исполнимостью, повторяемостью и рабочим результатом.

3. Переводит развитие из feature list в продуктовую программу
Потому что каждый спринт заканчивается не абстрактной доработкой, а усилением конкретного слоя продукта.

## 14. Короткий итог

Если упростить до одной фразы:

Нужно не «улучшать всё подряд», а последовательно довести:
- recurring core;
- assistant layer;
- file contour;
- прикладные сценарии;
- workflow layer;
- и только потом enrich-слои вроде dashboards.

Именно такая последовательность с наибольшей вероятностью превратит Hermes в внутренний продукт, а не в набор сильных, но разрозненных возможностей.
