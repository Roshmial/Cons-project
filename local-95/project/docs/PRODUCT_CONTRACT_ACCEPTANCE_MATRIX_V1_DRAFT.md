## 1. Зачем нужен этот документ

Этот документ фиксирует не общую концепцию продукта, а конкретный product contract:
- что Hermes обещает делать стабильно;
- что поддерживается с ограничениями;
- что пока не надо продавать как зрелый продукт;
- какой результат считается нормальным;
- какой fallback считается допустимым.

Главная цель:
убрать двусмысленность между capability, UX-ожиданием и реальным supported path.

## 2. Статусы поддержки

- Supported — продукт обещает это как нормальный и повторяемый сценарий.
- Guarded — сценарий поддержан, но должен идти через ограничения, fallback или дополнительную ясность для пользователя.
- Non-core — сценарий допустим как направление развития, но не должен подаваться как зрелый supported path.

## 3. Core block: Recurring / jobs / monitoring

| Сценарий | Статус | Ожидаемый результат | Допустимый fallback | Что не считать нормой |
|---|---|---|---|---|
| Создание job | Supported | Пользователь может создать задачу с понятными параметрами и сохранить её | Если параметры неполны — `needs_clarification` | Молчаливо создать неполную/непонятную задачу |
| Ручной запуск job | Supported | Пользователь может запустить задачу и увидеть факт запуска | Если задача стартовала, но результат ещё не готов — `running` | Неясно, стартовала задача или нет |
| Запуск по расписанию | Supported | Задача запускается по schedule без ручного участия | При временной ошибке — `failed` с причиной и возможностью retry | Тихое падение без статуса |
| Pause / resume job | Supported | Пользователь может приостановить и вернуть задачу в активный режим | Если действие невозможно — явная ошибка | Неявное изменение статуса |
| Подписка на результат | Supported | Пользователь может подписаться или отписаться от доставки | Если подписка не применена — явная ошибка | Неясно, подписка активна или нет |
| Просмотр run history | Supported | Пользователь видит историю запусков и их статусы | Если история недоступна — явная ошибка | Отсутствие различия между run и job |
| Успешный recurring output | Supported | Есть результат, пригодный к чтению и использованию | Краткий summary + ссылка/доступ к полному output | Пустой или непонятный вывод без объяснения |
| Empty result в monitoring | Supported | Система честно сообщает, что сигналов не найдено | `empty_result` с кратким пояснением | Выглядит как ошибка или молчаливый провал |
| Degraded result | Supported | Система показывает, что задача выполнена частично | `completed_with_limitations` + что именно не сработало | Подача частичного результата как полного |
| Failed run | Supported | Явно видно, что запуск не удался, и по какой причине | retry / inspect / handoff operator | Смешение failed и empty result |
| Triage / audit / digest jobs | Supported | Результат приходит в единообразном recurring формате | Краткий summary, даже если полный output вынесен отдельно | Каждый класс recurring outputs выглядит по-разному |
| Cross-entity workflow вокруг job | Guarded | Допустим перевод результата job в artifact / handoff | `guided_clarification` если следующий шаг неоднозначен | Автоматически угадывать дальнейший маршрут |

## 4. Core block: Assistant

| Сценарий | Статус | Ожидаемый результат | Допустимый fallback | Что не считать нормой |
|---|---|---|---|---|
| Обычный вопрос-ответ | Supported | Пользователь получает понятный ответ в чат | `needs_clarification`, если запрос слишком расплывчат | Псевдоуверенный ответ при отсутствии контекста |
| Вопрос с локальным контекстом | Supported | Ответ учитывает доступный контекст и профиль | Ограниченный ответ с пояснением, чего не хватает | Скрыто игнорировать важный контекст |
| Information gathering | Supported | Собран и структурирован релевантный материал | Частичный сбор с пометкой ограничений | Выдавать несобранную/непроверенную инфу как итог |
| Прикладной research | Guarded | Есть осмысленный рабочий обзор по теме | `completed_with_limitations` при неполных источниках | Притворяться, что coverage полный |
| Расчёты и модели | Guarded | Есть корректный расчёт или модельный вывод | `needs_clarification` при недостающих входных данных | Выдавать расчёт без явных предпосылок |
| Генерация таблиц | Guarded | Пользователь получает таблицу или структурированный табличный результат | Краткий текстовый summary, если таблица неуместна | Неструктурированный ответ вместо табличного, когда ожидалась таблица |
| Structured output | Supported | Ответ имеет понятную структуру, пригодную для использования дальше | Краткий summary + явное ограничение | Размытый разговорный ответ вместо рабочего результата |
| Перевод результата в artifact | Guarded | Пользователь может оформить результат как самостоятельный deliverable | Предложение сохранить/экспортировать после уточнения | Автоматически считать любой ответ артефактом |
| Перевод результата в job | Guarded | Если запрос recurring по смыслу, система может перевести его в job path | `needs_clarification` по schedule/delivery | Молчаливо превращать одноразовый запрос в recurring |
| Перевод результата в handoff | Guarded | Результат может быть подготовлен для следующего рабочего контура | `guided_clarification` по получателю/формату | Делать вид, что handoff уже выполнен, если это не подтверждено |
| Глубокий multi-step orchestration через chat | Non-core | Не обещать как штатный path | Разбить на поддерживаемые шаги | Продавать как зрелый workflow layer |

## 5. Core block: Files

| Сценарий | Статус | Ожидаемый результат | Допустимый fallback | Что не считать нормой |
|---|---|---|---|---|
| Upload файла | Supported | Пользователь может загрузить файл и увидеть факт загрузки | Явная ошибка, если файл не принят | Пропажа файла без статуса |
| Reuse файла из профиля | Supported | Пользователь может выбрать существующий файл как вход | `needs_clarification`, если выбор неоднозначен | Неясно, какой файл был использован |
| Text extraction | Supported | Для поддерживаемых форматов извлекается текст | `completed_with_limitations`, если extraction частичный | Выглядит как будто файл обработан полностью, когда это не так |
| Preview содержимого | Guarded | Пользователь видит полезный preview или summary | Краткий excerpt + пояснение лимита | Пустой preview без объяснения |
| Использование файла в ответе | Supported | Видно, что файл реально учтён в результате | Явное указание ограничений обработки | Файл приложен, но роль в результате неясна |
| Generated file как результат | Guarded | Система может выдать файл как deliverable | Artifact/summary, если файл не был реально сгенерирован | Подменять файл текстовым ответом без маркировки |
| Download / open file | Supported | Пользователь может получить доступ к файлу | Явная ошибка доступа | Неясно, файл существует или нет |
| Ошибка parsing / unsupported format | Supported | Пользователь честно видит, что файл не обработан или обработан частично | `failed` или `completed_with_limitations` | Тихо игнорировать проблему |
| Сложные document-heavy pipelines | Guarded | Допустимы в ограниченном режиме | Разбивка на несколько шагов | Обещать как зрелый end-to-end path |

## 6. Cross-cutting business scenarios

| Сценарий | Статус | Ожидаемый результат | Допустимый fallback | Примечание |
|---|---|---|---|---|
| Recurring monitoring / digest | Supported | Регулярный, читаемый, доставляемый output | `empty_result` или `degraded` | Главный differentiator продукта |
| КП draft | Guarded | Система помогает собрать и оформить draft КП | Уточнение структуры/входных данных | Пока не считать полностью шаблонизированным path |
| ТЗ draft | Guarded | Система помогает собрать draft ТЗ / dev-ready artifact | Частичный результат с ограничениями | Нужен отдельный прикладной contour в следующих спринтах |
| Почта / внутренние системы | Non-core | Пока не обещать как зрелую интеграцию | Handoff-prep / artifact preparation | Отдельный продуктовый слой позже |
| Workflow layer | Non-core | Не обещать как текущую зрелую функцию | Разбиение на chat / file / job / handoff | Стратегический следующий слой |
| Dashboards | Non-core | Используются как secondary visualization | Summary / artifact без dashboard | Не dashboard-first продукт |

## 7. Минимальный набор acceptance scenarios для ручной проверки

### Recurring
1. Создать job.
2. Запустить job вручную.
3. Увидеть `running`.
4. Увидеть итоговый статус run.
5. Увидеть разницу между `completed`, `failed` и `empty_result`.
6. Подписаться на результат.

### Assistant
1. Задать обычный вопрос.
2. Задать вопрос с приложенным контекстом.
3. Попросить research summary.
4. Попросить табличный результат.
5. Попросить оформить результат как следующий рабочий объект.

### Files
1. Загрузить файл.
2. Проверить preview/extraction.
3. Использовать файл в ответе.
4. Скачать/открыть файл.
5. Проверить реакцию на частично поддерживаемый или неудобный файл.

## 8. Что этот draft ещё не закрывает

Этот документ пока:
- не привязан жёстко к backend response schema;
- не привязан жёстко к frontend copy на каждом экране;
- не заменяет implementation backlog;
- не означает, что все guarded scenarios уже реализованы хорошо.

Он фиксирует продуктовую рамку, от которой уже можно вести backend/frontend cleanup Sprint 0.
