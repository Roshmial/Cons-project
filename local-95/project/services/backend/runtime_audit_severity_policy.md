[2026-06-24] Runtime audit severity policy

Назначение
Этот файл задаёт правила калибровки `severity` и обработки исключений для runtime audit в Hermes Web backend.

1. Базовые уровни severity

high
- сбой делает пользовательский результат недоступным или практически бесполезным;
- ошибка выглядит системной или инфраструктурно-критичной;
- повторение у нескольких пользователей резко повышает вероятность продуктовой проблемы.

medium
- результат частично деградирован, но пользователь всё ещё получил хоть какой-то полезный выход;
- проблема заметна, но не всегда блокирующая;
- ошибка может быть локальной, route-specific или связанной с нестабильным upstream.

low
- шум, одиночные неопасные отклонения, косметические деградации;
- поведение не выглядит блокирующим и не ломает основной пользовательский сценарий.

2. Текущий baseline mapping

Для `chat_task_error`:
- high:
  - `timed out`
  - `timeout`
  - `connection error`
  - `connection refused`
  - `service unavailable`
  - `internal server error`
- medium:
  - `bad gateway`
  - `gateway timeout`
  - `rate limit`
  - `rate limited`
  - `json decode error`
  - `invalid response`
- fallback rule:
  - если класс содержит `error`, но не попал в явный список, считать `medium`;
  - иначе по умолчанию `low`.

Для `chat_task_degraded_result`:
- high:
  - `empty_result`
  - `no_sources_found`
  - `sources_unavailable`
- medium:
  - `hybrid_content_plus_shortlist`
  - `sources_partially_unavailable`
  - `partial_result`
  - `degraded_result`
- fallback rule:
  - если event несёт `partial_result=true`, считать `medium`;
  - иначе по умолчанию `low`.

3. Правила калибровки по живым сигналам

Повышать severity стоит, если одновременно выполняется хотя бы одно из условий:
- класс регулярно повторяется у 2+ пользователей;
- класс повторяется сериями в соседних окнах 24h/72h;
- событие ведёт к пустому, бессодержательному или явно вводящему в заблуждение ответу;
- проблема затрагивает базовый маршрут, а не экзотический follow-up сценарий.

Понижать severity стоит, если выполняются все условия:
- событие одиночное;
- нет multi-user признака;
- пользователь всё равно получает приемлемый ответ;
- источник выглядит как внешний шум, тестовый след или кратковременный upstream-флап.

4. Правила override

Правило A: multi-user override
- если один и тот же класс повторяется у нескольких пользователей, его нельзя разбирать как обычный low-severity шум;
- минимум — вручную пересмотреть класс на `medium` даже если baseline-словарь оставляет его в `low`.

Правило B: empty-or-misleading output override
- если формально событие не выглядит тяжёлым, но фактически даёт пустой, бессмысленный или вводящий в заблуждение результат, класс нужно поднимать минимум до `medium`, а часто до `high`.

Правило C: recoverable external noise override
- если ошибка вызвана внешним флапом, быстро самовосстанавливается и не ломает пользовательский сценарий после retry/fallback, класс можно оставить на текущем уровне или понизить, но только с явной пометкой, что это именно внешний шум, а не продуктовый дефект.

Правило D: route-critical override
- если проблема бьёт по основному пользовательскому маршруту, её severity должна быть не ниже `medium`, даже если частота пока невысока.

5. Обработка исключений

Исключение 1: тестовый или harness-шум
- не повышать severity только из-за того, что ошибка выглядит страшно по строке;
- сначала отделить product failure от test/teardown/harness noise.

Исключение 2: единичный экзотический follow-up
- если проблема возникает только в редком follow-up path и не затрагивает базовый поток, стартовать с `low` или `medium`, а не автоматически ставить `high`.

Исключение 3: частый, но мягкий degraded outcome
- высокая частота сама по себе не делает класс `high`;
- если пользователь по-прежнему получает полезный ответ, класс может оставаться `medium`, даже при заметной повторяемости.

Исключение 4: редкий, но критичный empty result
- низкая частота сама по себе не делает класс безопасным;
- если результат пустой или по сути сломан, класс может быть `high` даже при единичных событиях.

6. Правила для triage

Приоритет разбора должен учитывать в таком порядке:
1. severity
2. multi-user охват
3. частоту
4. близость к основному пользовательскому маршруту

Если low-severity класс обгоняет high-severity класс по сырой частоте, triage обязан отдельно пояснить этот компромисс, а не молча сортировать только по count.

7. Когда обновлять policy

Policy надо пересматривать, если:
- накопились реальные повторяющиеся инциденты, которые плохо ложатся в текущие словари;
- один и тот же класс стабильно получает ручной override;
- появляются новые типы degraded outcomes, которые уже нельзя честно держать в generic bucket.

8. Чего policy не делает

Этот документ не заменяет root-cause analysis.
Он нужен для первичного ранжирования и для того, чтобы daily audit и triage вели себя последовательно, а не случайно.
